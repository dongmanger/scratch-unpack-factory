# Scratch 编译产物还原工厂 —— 交付包

`factory` 把 **TurboWarp / 02Engine 打包出来的 HTML 或 ZIP** 还原成可打开、可编辑的 `.sb3`。
它不是"猜积木"，每一步恢复都要么有源码级证据，要么经真实 02 编译器重编译验证过；做不到就如实报告未恢复，绝不伪造。

---

## 一、包内结构

```
factory/          工具本体（源码 + 测试 + 随包编译器 + 文档）
  src/            42 个模块，约 10 000 行
  test/           67 个测试文件，1195 个用例
  bench/          评分脚本（召回率 / 精确率）
  vendor/         02 编译器（7.2 MB，加载前先做 sha256 完整性校验）
  delivery/       打包脚本与指标
artifacts/        被还原的编译产物 + 真值工程
  o2/             02Engine 打包件（plain / strong 混淆）
  tw/             TurboWarp 打包件
  ground-truth/   作者原始 .sb3，用来算召回率
output/           工具对这些产物的实际输出（sb3 + 保真报告）
metrics/          召回率 / 精确率实测数据
manifest.json     逐文件 sha256
```

---

## 二、怎么跑

```bash
cd factory
npm install            # 需要 Node >= 20
node bin/factory.mjs unpack <产物.html|zip> -o <输出目录>
```

常用参数：

| 参数 | 作用 |
|---|---|
| `--recovery oracle\|strict` | 恢复模式，默认 `oracle`（见下） |
| `--no-beautify` | 关闭结构美化、布局重排、代码美化 |
| `--allow-partial` | 部分恢复时也返回 0 |
| `--overwrite` | 覆盖已有输出 |

退出码：`0` 完整保留 / `2` 结构无效 / `3` 部分或未验证重构。

**块膨胀 0.83x** 是关键：产物块数少于真值，说明没有自造积木（对比同类工具常见的 3.6× 膨胀）。

> **`artifacts/tw/10128407-zip.zip` 未列入指标**：该输入本身有 59 处广播名大小写不一致（引用写 `"Spawn Chunk from Seed"`，定义是 `"spawn chunk from seed"`），是 TurboWarp 打包时的既有缺陷。工具如实判为 `invalid` 并列出每一条，这是正确行为，不是还原失败。同目录的 `437419376-zip.zip` 无此问题，100% 通过。

### 两种恢复模式的差距

| 模式 | 脚本召回 | 脚本精确 | 说明 |
|---|---|---|---|
| `oracle`（默认） | 77.5% | 88.5% | 每项恢复都经真实 02 编译器重编译验证 |
| `strict` | 18.1% | 40.1% | 只接受能静态证明的形态 |

**oracle 是 strict 的 4.3 倍召回。** 这是本项目最核心的机制：先大胆提出积木假设，再让真实编译器裁决——编译器把积木编回与产物完全相同的 JavaScript，才保留；否则降级或丢弃。

## 四、这些数字的边界（重要）

1. **77.5% 是"脚本签名完全一致"的严格口径。** 按"过程定义是否存在"算，实际恢复率是 **93.8%（271/289）**。差的 15 个百分点是体内容差异，主因是编译器优化造成的不可逆损失（`if/else` 折叠、循环展开、常量折叠），不是解码失败。

2. **88.5% 的精确率被匹配方式压低了。** 一个过程体内容不一致时，会在多重集匹配里同时算"漏掉真值"和"多出候选"，双重扣分。

3. **剩下 22.5% 的召回缺口在哪**（116 个脚本）：
   - 54 个 `procedures_definition`：其中 33 个是过程体完全没恢复，21 个是体内容不一致
   - 21 个广播接收帽子：帽子在，体内容不一致
   - 12 个 `operator_not` 顶层游离积木：作者留在舞台边缘的未连接积木，本身极短
   - 其余为 `control_if`、`operator_*` 等零散项

4. **已知不可恢复项**：`Math.atan(NaN)`、`target.interpolationData` 这类运行时内部状态没有对应积木；循环展开的逆识别需要推断循环边界，误判风险高，本次未做。

5. **保真度分层**：容器字节、素材、变量/广播名与作用域 ID 是 100% 无损；积木代码按证据分级；原图布局与内部 ID 在 precompile 后永久丢失，报告里明确标注。

## 五、报告怎么看

每次运行产出 5 个文件：

| 文件 | 内容 |
|---|---|
| `*.sb3` | 还原出的工程 |
| `*.fidelity-report.json` | 完整证据：逐脚本状态、置信度、重编译判定、素材哈希 |
| `*.fidelity-report.md` | 同上，人读版 |
| `*.compiled-project.json` | 产物里提取的编译包原文（证据留存） |
| `*.deobfuscated-compiled-project.json` | 解混淆后的编译包 |

**置信度是规则证据分，不是统计概率**：原图保留 1.0、metadata 帽子 0.98、封闭模板 0.85、重编译验证 0.95、未恢复 0。

报告里 `code.beautify` 分三个字段：`applied`（结构改写是否真发生）、`layoutApplied`（布局是否重排）、`enabled`（确实改写了）。默认 oracle 模式只重排布局，不改写结构——因为折叠布尔双重否定会让积木重编译出与产物不同的 JavaScript，无法通过校验。需要结构改写用 `--recovery strict`。

## 七、安全说明

- 静态提取不执行输入代码；`--mode dynamic` 才会启动浏览器执行，需明确授权
- `vendor/02-vm.cjs` 加载前先做 sha256 完整性校验（CommonJS 顶层代码会在 require 时执行，顺序不能反）
- ZIP 路径遍历防护、炸弹防护（条目数 / 单条目 / 总量 / JSON 四重限额）
- `verify` 命令要求显式 `--allow-execute`，且报告明确声明 worker 隔离**不是**安全沙箱
